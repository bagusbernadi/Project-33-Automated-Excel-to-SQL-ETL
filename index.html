Project 33: Automated ETL: Excel Log → SQL Database

Tujuan project: membangun pipeline ETL otomatis yang membaca log Excel operator yang berantakan, membersihkan dan memvalidasinya, lalu memuatnya ke database SQL, untuk mengukur seberapa banyak data yang bermasalah dan berapa jam kerja yang bisa dihemat, sehingga laporan produksi bisa disusun dalam hitungan menit.

Kategori:Rancangan projectManufaktur smartphoneData simulasiPython ETL + SQL

Project Introduction

Bayangkan kantor pos yang menerima ribuan surat setiap hari. Alamatnya ditulis dengan cara yang berbeda-beda: ada yang lengkap, ada yang menyingkat nama kota, ada yang tulisannya sulit dibaca. Petugas harus merapikan alamat, menyisihkan surat yang alamatnya tidak lengkap, lalu menyusun surat di rak sesuai tujuan.

Log produksi di pabrik mirip dengan tumpukan surat itu. Setiap stasiun punya file Excel sendiri, formatnya berubah dari bulan ke bulan, dan cara menulis tanggal atau nama model tidak seragam. Sebelum laporan bisa dibuat, seseorang harus merapikan semuanya secara manual.

Project ini membangun pipeline ETL yang bisa dijalankan ulang kapan saja: semua file Excel dibaca, dirapikan, divalidasi, lalu dimuat ke database tanpa menggandakan data. Project 30 mencegah data kotor sejak input, sedangkan project ini merapikan log lama yang sudah terlanjur berantakan. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Gambaran alur kerja di lini perakitan smartphone

Lini produksi bisa dibayangkan sebagai tiga jalur. Jalur pertama adalah proses produksi. Jalur kedua adalah cara laporan disusun saat ini. Jalur ketiga adalah yang dibangun di project ini.

  1. Jalur produksi. Komponen melewati 10 stasiun, dari Solder Paste Printing sampai Packaging. Setiap stasiun mencatat input, OK, dan NG di log Excel masing-masing.
  2. Pelaporan saat ini. Engineer mengumpulkan file dari setiap stasiun, menyalin datanya ke satu file, merapikan format, lalu menghitung KPI secara manual.
  3. Extract dan transform. Program membaca semua file sekaligus, mengenali format yang berbeda, lalu menyeragamkan tanggal, model, shift, dan nama kolom.
  4. Validasi, load, dan laporan. Baris yang lolos validasi dimuat ke database, baris yang gagal masuk karantina. Laporan dibuat otomatis dari database.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di lini perakitan smartphone, setiap stasiun mencatat hasil produksi di file Excel sendiri. Template-nya pernah diubah beberapa kali dan setiap operator punya kebiasaan menulis yang berbeda. Akibatnya:

  • Menyusun laporan bulanan berarti membuka puluhan file, menyalin data, dan merapikan format satu per satu.
  • Penulisan model (Pro, PRO, "Model Pro") dan tanggal yang tidak seragam membuat rumus Excel salah menghitung tanpa disadari.
  • Merged cell, baris subtotal, dan baris kosong di tengah data membuat file sulit dibaca program.
  • Tidak ada catatan baris mana yang dibuang atau diperbaiki, sehingga angka laporan sulit dipertanggungjawabkan.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Merekap log Excel operator adalah pekerjaan rutin Process Engineer, dan masalah formatnya dialami langsung.
  • Menunjukkan skill data engineering dasar. Membaca file berantakan, cleaning, validasi, load yang aman dijalankan ulang, rekonsiliasi, dan test.
  • Tingkat kesulitan sulit. Analisisnya sederhana, tetapi menangani banyak format dan menjaga hasil tetap konsisten butuh ketelitian.
  • Terhubung dengan project lain. Database hasil ETL bisa dipakai Project 3 (Yield, Rework & Defect Tracking) dan Project 23 (Telegram Bot KPI Reporting), dan melengkapi Project 30 serta Project 25 (Messy Excel Report Parser).

3. ETL Flow & Data QualityKomponen tambahanBagaimana setiap baris diproses, dan berapa waktu yang bisa dihemat

Data yang masuk database harus bisa dipertanggungjawabkan. Karena itu setiap baris yang ditolak dicatat beserta alasannya, bukan dibuang diam-diam. Arahkan kursor atau klik kata yang diberi garis bawah kuning untuk melihat pengertian dan rumusnya.

Alur satu baris data

Baris yang gagal validasi tidak diperbaiki diam-diam. Baris itu masuk karantina beserta alasannya, lalu bisa diperbaiki dan dimuat ulang.

Berapa jam penyusunan laporan yang bisa dihemat

Setiap batang adalah satu langkah menyusun laporan produksi, dalam menit per laporan (angka contoh, bukan hasil dari data). Batang muda menunjukkan waktu manual, batang biru menunjukkan sisa waktu setelah ETL. Klik sebuah langkah untuk menyalakan atau mematikan otomatisasinya, lalu geser slider untuk mengatur jumlah laporan per bulan.

4. DatasetLog Excel simulasi yang meniru kebiasaan pencatatan di lini perakitan smartphone

Kenapa data simulasi? Log produksi asli bersifat rahasia. File Excel dibuat dengan program Python yang meniru masalah nyata: template yang berubah, penulisan yang tidak seragam, merged cell, dan baris subtotal. Karena masalahnya sengaja ditanam, hasil ETL bisa diperiksa satu per satu.

Ukuran: 10 stasiun, 3 model, 2 shift, ±6 bulan, sekitar 60 file Excel. Perkiraan jumlah baris: ±7.000 baris produksi (stasiun × model × shift × hari). Jumlah pastinya baru diketahui setelah data dibuat.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_messy_logs.py di repositori project (Versi: v1, rancangan; Tanggal dibuat: saat Tahap B dikerjakan). Tidak memakai data perusahaan.

Fakta yang sengaja ditanam (ground truth)

1. Tiga versi template: kolom berbeda urutan dan nama (misalnya "Qty OK" dan "OK"), termasuk satu template khusus AOI Inspection.

2. Format tanggal campuran: 02/08/2026, 2026-08-02, dan angka serial Excel.

3. Nama model ditulis beragam: Pro, PRO, pro, dan "Model Pro".

4. Merged cell di judul, baris subtotal, dan baris kosong di tengah data.

5. Sekitar 2–3% nilai tidak valid: jumlah negatif, OK + NG lebih dari input, baris ganda, dan shift kosong. Selain itu, NG di Reflow Soldering dibuat naik di bulan ke-4.

Empat tabel yang akan dibuat

Data mentah disimpan apa adanya di tabel staging, lalu baru dipindahkan ke tabel bersih setelah lolos validasi. Dengan begitu setiap angka di laporan bisa ditelusuri kembali ke file dan baris asalnya.

5. ToolsAlat yang dipakai dan alasannya

Python (pandas, openpyxl)

openpyxl membaca file Excel termasuk merged cell, pandas merapikan dan menyeragamkan data. Pipeline dijalankan dengan satu perintah.

Sesuai kolom Tools di daftar portofolio (Python, SQL).

DuckDB + SQL

Database tujuan. Load memakai kunci unik sehingga run ulang tidak menggandakan data. SQL dipakai untuk query analitik dan rekonsiliasi.

Gratis, satu file, dan konsisten dengan project lain di portofolio ini.

Pandera (opsional)

Menuliskan aturan validasi sebagai schema yang rapi, sehingga aturan mudah dibaca dan diuji.

Jika tidak dipakai, aturan ditulis sebagai fungsi Python biasa.

pytest + GitHub Actions

Unit test untuk setiap aturan transform dan validasi, uji run ulang, dan rekonsiliasi. Dijalankan otomatis setiap ada perubahan kode.

Bukti bahwa pipeline aman diubah tanpa merusak hasil lama.

Streamlit + Plotly

Laporan produksi otomatis dan halaman kualitas data: load rate, reject rate per stasiun, dan isi karantina.

Semua tetap di Python dan bisa dibuka lewat link.

Excel + GitHub

Excel dipakai untuk cek silang total dengan file asli. GitHub menyimpan kode, aturan, dan README.

Rekan kerja bisa memverifikasi hasil dengan alat yang sudah biasa dipakai.

9. Assumptions & LimitationsKomponen tambahanKeputusan yang sudah diambil dan hal yang perlu diwaspadai

Tools: DuckDB + Streamlit + Plotly Sudah Anda setujui

Konsisten dengan project lain. Kolom Tools di daftar portofolio hanya menulis Python dan SQL, sehingga DuckDB dan Streamlit sebaiknya ditambahkan.

Jenis data: simulasi Usulan awal

Sesuai kolom Sumber data di daftar portofolio. File Excel dibuat dengan program dan meniru masalah format di lini perakitan smartphone. Angka hasil akhir membuktikan pipeline bekerja, bukan menggambarkan kondisi pabrik sebenarnya.

Ruang lingkup Usulan awal

10 stasiun perakitan smartphone, model Basic, Plus, dan Pro, 2 shift, ±6 bulan, 3 versi template. Baris yang gagal validasi dikarantina, bukan diperbaiki otomatis. Dampak dihitung dalam jam kerja, belum dalam rupiah.

Hal yang perlu diwaspadai Usulan awal

File asli lebih beragam. Log Excel di lapangan bisa memiliki masalah yang tidak ada di simulasi. Pemetaan kolom disimpan di file konfigurasi agar mudah ditambah.

Perbaikan otomatis bisa keliru. Menebak nilai yang salah bisa membuat data tampak benar padahal tidak. Karena itu baris bermasalah dikarantina dan diputuskan manusia.

Estimasi waktu. Menit per laporan sebelum ETL adalah asumsi. Angka sebenarnya sebaiknya diukur dengan stopwatch pada beberapa laporan.

Pola belum tentu penyebab. Kenaikan NG di Reflow Soldering baru pola. Penyebabnya perlu dicek di lapangan, dan pengujian statistik dikerjakan di Project 29.
